    \section{The need for maintenance and update of the scientific databases}

    Nowadays, all researchers are using databases. From the very well-known scientific literature database PubMed to highly specialized databases, such as JASPAR \cite{canese2013pubmed,rauluseviciute2024jaspar}. Since it is such a trivial everyday activity, many do not put much thought into how these databases come to be and what effort is needed to keep them running. A lot of effort from teams of people is put in to maintain and update scientific databases. For example, the JASPAR database is updated every 2 years, which means that for 2 years an international team of people mines and processes the motif data, then manually curates it, while also constantly updating data processing pipelines, developing new tools and maintaining the old ones. Last, but not least, in addition to preparing a new release, the JASPAR team is monitoring the user feedback: addressing potential errors and bugs in data and tools and taking suggestions that could be incorporated into the new release.

    One of the biggest aspects of the JASPAR database that distinguishes it from other similar databases, is that JASPAR relies on manual motif curation. It is often underappreciated how much manual labor might be needed to maintain the quality of the data. Today with a variety of computational tools, a lot of such labor can be eased, but often the final say comes from a researcher. For example, for JASPAR database update motifs are prepared using a computational pipeline, and the top three most central motifs from each peak dataset are selected for further inspection \cite{bailey2012inferring}. These motifs can have the same centrality values, so there is no automatic way to select the best of them. Thus, the curator then evaluates the motifs visually and searches the literature to select the best, if any of them are good at all. Another example of the effort to increase the quality of the data in databases is revising and refining the classification of the transcription factors. Revising the metadata for current profiles is a separate initiative that might not be seen as a priority compared to adding more new data. Since 2022, we put extra effort into updating the metadata of already existing profiles, including searching for orthogonal support for profiles in the UNVALIDATED collection. For the 2024 release, we used a new plant TF classification Plant-TFClass to update the metadata for all plant transcription factors in JASPAR \cite{blanc2024plant}. Unfortunately, for other taxa, such as nematodes or insects, we have to rely on unsystematic annotations to assign TF classes and families. Notably, in the latest release, a lot of new data was added particularly for these two taxa. This is a great motivation to pay attention to other than vertebrate taxa in future updates of the database.

    User input is very important when managing a database. In JASPAR users can provide feedback using a Q\&A forum. Occasionally we receive reports on potential bugs, which results in a clarification for the user or the actual fix in the database. In addition, the user questions and feedback can help to clarify the documentation of the database or give ideas on how JASPAR could be improved in the upcoming release. Finally, we provide a specific form along with the UNVALIDATED profiles for the users to submit possible validation references. We aim to find the orthogonal support for all the UNVALIDATED profiles, so JASPAR users can become part of this. It is important to provide an attractive environment for users to engage with the database not only to access and download the data but also to provide feedback. This helps to ensure the quality, accuracy, and relevance of the data.

    Some efforts aim to enhance the automatic data usability by machines, in addition to supporting its usage by individual researchers. Good data management supports scientific discoveries. \ac{FAIR} serves as a guide for data producers and publishers \cite{wilkinson2016fair}. Briefly, findable means that the data is described with rich metadata, which is clear and identifiable. Accessible means that the data and its metadata can be accessed using a unique identifier, the protocol is open and free, and metadata should be accessible even when the data is no longer available. Interoperability means that the metadata follows FAIR-compatible vocabulary, includes references to other sources, and generally uses formal and broadly applicable language. Finally, reusability implies that data and metadata are released with clear usage license and meet relevant to the community standards \cite{wilkinson2016fair}. These principles should be applied also to the algorithms, tools, and workflows that were used to produce the data. The authors of FAIR emphasize that beyond high-quality production of the data, it is important to include a notion of "long-term care" of digital assets. The care of such assets includes ethical considerations for personal data. Specific guidelines for sensitive data are created and should be followed. In JASPAR database FAIR principles are followed. The database is open-access and provides the data in conventional formats, such as JASPAR, MEME, TRANSFAC, and RAW-formatted frequency matrices for TF binding. Motif instances are provided in well-known BED and FASTA formats. The metadata associated with each profile is provided whenever possible. However, it is important to note that the amount of the metadata highly depends on its availability in the source of the data. All this data can be accessed in various ways: user-friendly website, Python and Bioconductor packages, and API. Users can choose the most comfortable to them access. The results, generated by the COBIND pipeline are also freely available as a user-friendly interactive webpage. Users can browse the page directly and download associated data.

    Accessibility of the data is an essential aspect of the research \cite{tedersoo2021data}. However, open access is not commonly accepted. Some researchers would even consider computational biologists, who use published experimental data as "research parasites" \cite{longo2016data}. The bioinformatics community actively promotes open data sharing since the development of the field. A couple of the best examples of data sharing are the Human Genome Project and the ENCODE project \cite{international2001initial,encode2012integrated}. Without data sharing, a lot of expensive experimental data would remain understudied. There are several repositories, such as ZENODO and Figshare, that are used to store and retrieve large data. Importantly, these repositories assign the \ac{DOI} allowing the proper crediting of the producers of that data \cite{zenodo,singh2011figshare}. With computational methods evolving, the already produced data can be analyzed again or differently to give new scientific insights. For example, DNase I hypersensitivity data from ENCODE was used by Vierstra \textit{et al.} to compute the DHS footprints \cite{vierstra2020global}. Since ENCODE data was also used in UniBind, thus for COBIND, I was able to reuse the footprints to analyze the co-binding patterns in footprints in matching cell types. However, the FAIR principles are essential to make the metadata clear to ensure this kind of reusability. In this case, cell types were matched successfully because the data came from the same original resource, ENCODE, and was well-preserved in the subsequent studies. To summarize cell type information for data that comes from many sources is still a very difficult task. Some resources, such as BRENDA \cite{gremse2010brenda}, provide tissue ontologies, but to apply it to the metadata would still require manual input.

    To be able to find the data, access it, use it to develop tools, and then produce more data, while navigating and entangling complex biological questions --- that is the job of a bioinformatician. Being able to do it freely and then make it available to fellow researchers --- that is what every researcher should aim for. Scientific databases are an essential part of a researcher's life. Well-used databases must be updated and maintained to ensure the research progress.

    \section{Development of new bioinformatics tools}

    Besides using scientific databases, researchers use computational tools. Some of these tools are commercial and come with laboratory equipment, but many are developed by individual bioinformaticians or small groups of researchers. The latter category of tools can exist as command line tools, packages (Bioconductor, R, Python), or pipelines (Nextflow, Snakemake) \cite{gentleman2004bioconductor,r2023language,python2009language,di2017nextflow,molder2021sustainable}. The quality of this software varies from extremely easy to use to unusable, unmaintained tools. The lack of software quality in bioinformatics can hinder the progress of research because a lot of time is used to debug or adapt already existing tools. Whenever a new bioinformatics tool is being developed, certain software quality aspects should be followed.

    The scientific code should always be organized to make it easier to use. It could be organized into a package or a pipeline. For example, COBIND has quite a simple organization. It is written as a collection of scripts, but all of them are organized into a Snakemake pipeline, which is parameterized using a configuration file. JASPAR is much more complex from a software perspective. The update of the database relies on many individual software pieces. In 2024, we summarized them into three big software components, "3D", that are organized into pipelines. (1) The "\textbf{D}iscovery" pipeline in Snakemake discovers motifs from peak data or processes external motifs and prepares them for manual curation. (2) The "\textbf{D}ownstream" pipeline (now also implemented in Snakemake) collects curated motifs and prepares all additional results and data needed for the website. (3) The "\textbf{D}eployment" pipeline, now organized as an Ansible playbook and launched using the Jenkins platform, takes care of creating the updated website. The first and second components are intercepted by manual curation, while the second and third are separated by data collection and moving into an appropriate place. Even with the manual curation step it is possible to connect all the components needed to perform a complex task, such as database update. Organizing scientific software into pipelines is not the only solution, but for the user, pipelines are relatively easy to understand and follow.

    Developing a pipeline or a package can be a personal choice as long as the software is usable. One of the biggest challenges when trying to reuse someone else's written software is dependency management. Therefore, dependency management should be one of the priorities when developing a new tool. It is important to provide dependency requirements in the documentation of the tool. There are several automated ways to manage dependencies and ensure that the tool will work as intended. Virtual environments isolate tool dependencies from a global environment, ensuring that appropriate packages are present and will be used by the tool. One of the most popular tools for virtual environment management is Conda \cite{anaconda}. The more recent and great way to isolate the entire software is by building software containers. Containers can isolate everything from the code itself to the system libraries and settings. From the user's perspective, downloading the container is enough and none of the dependencies needs to be installed, besides the tool that runs the container. The most widely used containerization tools in bioinformatics are Singularity and Docker \cite{kurtzer2017singularity,merkel2014docker}. Singularity containers can be integrated into Snakemake workflows, which makes those pipelines very convenient. Built containers can be placed into repositories, such as Docker Hub (\url{https://hub.docker.com/}) for open access and version control. Both COBIND and JASPAR software are containerized using Docker (\url{https://hub.docker.com/repositories/cbgr}). Since JASPAR consists of multiple software components, several containers are built and combined in the different Snakemake pipelines. COBIND container provides the necessary environment to run the pipeline.

    Finally, an essential aspect of scientific software quality is proper version control, accessibility, and documentation of the code. This should be applied not only to the bioinformatics tools but to all scientific code that was written for data analysis. It is the only way to ensure the transparency and reproducibility of the published results. Tools, such as Bitbucket (\url{https://bitbucket.org/}) or GitHub (\url{https://github.com/}) provide all functionalities for code storage, the control of version and releases, and documentation. These practices are useful not only to the potential users but for the bioinformaticians themselves. Using branches, and writing appropriate commit messages will help when developing the code. Proper README documentation should inform what the software is about, the usage, the required and optional inputs, and the expected output. Both, JASPAR and COBIND software are freely available and extensively documented on Bitbucket.

    Following good software development principles gives confidence to the users and motivates them to use the tools. With the reproducibility crisis in science \cite{baker20161}, it is extremely important to invest time in the development and maintenance of high-quality, user-friendly software.
