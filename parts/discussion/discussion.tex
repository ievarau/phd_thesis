    \section{The need for maintenance and update of the scientific databases}

    Nowadays, every researcher is using some kind of database. From the very well-known scientific literature database PubMed to highly specialized databases, such as JASPAR \cite{canese2013pubmed,rauluseviciute2024jaspar}. Since it is such a trivial everyday activity, many do not put much thought into how these databases come to be and what effort is needed to keep them running. Sometimes it is assumed that they were once created and now keep themselves alive. In reality, a lot of effort from teams of people is put in every day to maintain and update scientific databases. For example, the JASPAR database is updated every 2 years, which means that for 2 years an international team of people mines and processes the motif data, then manually curates it, while also constantly updating data processing pipelines, developing new tools and maintaining the old ones. Last, but not least, in addition to preparing a new release, the JASPAR team is monitoring the user feedback: addressing potential errors and bugs in data and tools and taking suggestions that could be incorporated into the new release.

    Manual curation
    Manual curation of the data
    It is often underappreciated how much manual labor might be needed to maintain the quality of the data. Nowadays with a variety of computational tools, a lot of such labor can be eased, but often the final say comes from a researcher. For example, for JASPAR database update motifs are prepared using a computational pipeline. Top 3 motifs that are selected for the curation can have the same centrality values, so there is no automatic way to select the best of them. And centrality is only one criteria. Thus, the curator then evaluates the motifs visually and searches the literature to select the best, if any of them are good at all.
    Another example of the effort to increase the quality of the data in databases is revising and refining the classification of the transcription factors. It is a separate effort that many might not see as needed. For 2024 release plant TF classification was created and we were able to use this new classification and update the metadata for all plant transcription factors in JASPAR. Unfortunately, but for other taxons, such as nematodes or insects, we have to rely on unsystematic annotations to assign TF classes and families.



    User input is very important when managing a database, such as JASPAR. However, to receive such feedback, the database has to be user-friendly in the first place. 
    Graphical interfaces
    Platform to provide feeback - Q\&A


    Some efforts aim to enhance the automatic data usability by machines, in addition to supporting its usage by individual researchers. Good data management supports scientific discoveries. FAIR, which stands for Findability, Accessibility, Interoperability, and Reusability, serves as a guide for data producers and publishers \cite{wilkinson2016fair}. These principles can be applied also to the algorithms, tools, and workflows that were used to produce the data. The authors of FAIR emphasize that beyond high-quality production of the data, it is important to include a notion of "long-term care" of digital assets. The care of such assets includes ethical considerations for personal data. Specific guidelines for sensitive data are created and should be followed. In JASPAR database FAIR principles are followed. Database is open-access and provides the data in conventional formats, such as JASPAR, MEME, TRANSFAC and RAW-formatted frequency matrices for TF binding. Motif instances are provided in well-known BED and FASTA formats. The metadata associated with each profile is provided whenever possible. However, it is important to note that the amount of the metadata highly depends on its availability in the original source of the data. All this data can be accessed in various ways: user-friendly website, Python and Bioconductor packages, and API. Users can choose the most comfortable to them access. The results, generated by COBIND pipeline are also freely available as a user-friendly interactive webpage. Users can browse the page directly and download associated data.


    One of the FAIR principles is accessibility. It is worth highlighting because even today open access to the resources is not commonly accepted. Some researchers even went on to publish their opinion stating that computational biologists, who use published experimental data are "research parasites".
    A very important thing to mention when discussing data usability is open-access. 
    "Research parasites" according to some researchers. But a lot of data remains understudied. Examples of open-access data, such as ENCODE, are excellent. Data can be used in multiple studies and keep producing the scientific insights. For example, DHS data from ENCODE was used by Viestra et al. to compute the DHS footprints. Since ENCODE data was also used in UniBind, thus for COBIND, I was able to reuse the footprints to analyse the footprints in matching cell types. So the experimental data is not meant to be analysed once with one particular pipeline. If researchers store it well with good annotations, data will be reused multiple times. However, the need for proper annotation should be emphasized here. In particular, cell type annotations. We should come up with consensus annotations, so data from multiple experiments could be easily integrated together.
    There are some cell type annotations available, but it is still challenging to apply them to large collections of data. 
    BRENDA is tissue type ontology. Hard to automatically annotate large numbers of datasets. Needs manual interference to achieve best results.

    To be able to find the data, access it, use it to develop tools, to produce more data, while navigating and entangling complex biological questions --- that is the job of a bioinformatician. Being able to do it freely and then make it available to fellow researchers --- that is what every researcher should aim for.

    \section{Development of new bioinformatics tools}

    Besides using scientific databases, every researcher nowadays uses computational tools. Some of these tools are commercial and come with laboratory equipment, but many are developed by individual or small groups of researchers --- bioinformaticians. The latter category of tools can exist as command line tools, packages (Bioconductor, R, Python), or pipelines (Nextflow, Snakemake). The quality of this software varies from extremely easy to use to unusable, unmaintained tools. Certain software quality aspects make some tools much more used and more easily maintained.

    Choosing the right implementation platform
    Package, pipeline
    There is no single correct answer.

    Version control, public access via Bitbucket or GitHub

    Easing the usage through dependency management
    Containers, Conda
    Ease of use - web interfaces are good, but limited. Usually, they do not allow for large inputs, take time and downstream analysis of the results can be complicated due to the limited output (for example, often you cannot download the results as tables). The next thing to move to is containerization of command line tools. This would allow to use the tool in its full capacity, but in a much more user-friendly way. Arguably, containerized applications are easy to use for researchers with very limited experience in coding.
